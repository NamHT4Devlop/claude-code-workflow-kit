Part A — Security approval

A1. What the kit is, and is not

It is a Claude Code plugin: about thirty Markdown prompts (skills/, commands/, agents/), a handful of shell scripts (scripts/, hooks/) and three small Node programs that turn Markdown or a call graph into a self-contained HTML page. There is no daemon, no server, no account, no API key of its own, no package it installs. The full executable-surface audit, with the grep commands to reproduce it, is in SECURITY.md.

It is not a sandbox, a DLP control, or something that changes what Claude Code may do with the model. The model reads code — that is inherent to using an AI coding agent: when Claude reads a file, that text enters the model context under your company's Claude plan terms (Team/Enterprise: commercial terms, no training on your data by default). The kit adds no other egress:

Network / process useWhenWhere to
Telemetry, analytics, “phone home”never—
Generated HTML loading a chart libraryonly at view-time, and only when vendor/ is absentcdnjs.cloudflare.com (Mermaid / Cytoscape). With vendor/ present — the default, SHA-256 pinned in vendor/SHA256SUMS — the page makes zero external requests. No data is sent either way.
shadow-parity.cjs (parity harness of /cwk-rails-to-spring)only when a user runs itthe two --source/--target URLs on its command line
/cwk-splunk-report (a prompt)only when a user runs itSplunk / Slack through MCP or env credentials the company configured; nothing hardcoded
VS Code extension (optional)on a button clickspawns the local claude CLI; no network of its own

grep -rnE "child_process|execSync|spawn|\beval\(|new Function|http\.|https\.|fetch\(|net\.|dns\." \
  --include='*.js' --include='*.cjs' --include='*.sh' --include='*.ts' .
bash tests/run.sh          # every guard rule and every script that writes outside the repo is pinned by a test

A2. Deploying the guards as policy

Two PreToolUse hooks ship with the kit. Installed by an engineer in their own ~/.claude/settings.json they are a habit; installed by you from managed settings, with the hook files owned by root/admin, they are policy the user and the agent cannot remove.

HookMatcherWhat it does
hooks/git-guard.shBashAllows read/sync-in git (fetch · pull · status · log · diff · add · commit …) and gh reads; denies push and gh writes to any repository outside the whitelist, every way of retargeting git (remote, -c/config outside a key allowlist, GIT_*=, url.*.insteadOf), git/gh hidden in sh -c/python -c strings, and destructive local git (reset --hard, clean -f, rebase, branch -D, commit --amend …). Fails closed without jq.
hooks/file-guard.shEdit|Write|MultiEdit|NotebookEdit and BashBlocks Edit/Write and shell writes to settings.json, the hooks, ~/.gitconfig, .git/config, ~/.ssh, ~/.aws (and ~/.config/gh, ~/.netrc, the audit log). Reads stay allowed. Fails closed without jq.
1

Install the hook files read-only, owned by root/admin

# macOS / Linux — from a reviewed checkout of the kit, pinned to a tag
sudo mkdir -p /usr/local/lib/cwk
sudo install -o root -g wheel -m 0755 hooks/git-guard.sh  /usr/local/lib/cwk/git-guard.sh    # Linux: -g root
sudo install -o root -g wheel -m 0755 hooks/file-guard.sh /usr/local/lib/cwk/file-guard.sh
ls -l /usr/local/lib/cwk/                       # -rwxr-xr-x root … — nobody but root can rewrite the policy
which jq || echo "install jq: both hooks deny everything without it"
2

Set the company whitelist in the root-owned copy

The whitelist lives inside git-guard.sh on purpose — an environment variable would be one more thing the agent could set. Edit the two lines at the top of the copy you just installed (they compose ALLOW_OWNER_RE and ALLOW_GH_REPO_RE):

ALLOW_OWNERS='acme-org|acme-platform'       # GitHub orgs/users the agent may push to (regex alternatives)
ALLOW_HOSTS='github\.com|ghe\.acme\.example'  # github.com and/or your GitHub Enterprise host
# strictest: ALLOW_OWNERS='__NONE__' — the agent pushes nowhere; engineers push from their own terminal
3

Wire both hooks and the deny list from managed settings

Path per OS: /Library/Application Support/ClaudeCode/managed-settings.json (macOS) · /etc/claude-code/managed-settings.json (Linux/WSL) · C:\Program Files\ClaudeCode\managed-settings.json (Windows). Claude Code applies this file above every user, project and --settings value; hooks and permissions.deny set here cannot be overridden. Make the file itself root-owned and 0644.

{
  "permissions": {
    "deny": [
      "Bash(git remote add:*)", "Bash(git remote set-url:*)", "Bash(git remote remove:*)",
      "Bash(git reset --hard:*)", "Bash(git clean -f:*)", "Bash(git rebase:*)",
      "Bash(git commit --amend:*)", "Bash(git restore:*)", "Bash(git branch -D:*)",
      "Bash(git send-email:*)",
      "Read(~/.ssh/**)", "Read(~/.aws/**)", "Read(**/.env)", "Read(**/.env.*)",
      "Bash(curl *| sh*)", "Bash(curl *| bash*)", "Bash(wget *| sh*)", "Bash(sudo:*)",
      "WebFetch"
    ]
  },
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash", "hooks": [
        { "type": "command", "command": "/usr/local/lib/cwk/git-guard.sh",  "timeout": 10 },
        { "type": "command", "command": "/usr/local/lib/cwk/file-guard.sh", "timeout": 10 } ] },
      { "matcher": "Edit|Write|MultiEdit|NotebookEdit", "hooks": [
        { "type": "command", "command": "/usr/local/lib/cwk/file-guard.sh", "timeout": 10 } ] }
    ]
  }
}

There is deliberately no blanket Bash(git push:*) deny: the hook decides a push by its target, so pushes to the whitelisted org still work. Verify on a machine after a Claude Code restart:

printf '{"tool_name":"Bash","tool_input":{"command":"git push https://github.com/some-other-org/x"}}' | /usr/local/lib/cwk/git-guard.sh
# → {"hookSpecificOutput":{…"permissionDecision":"deny"…}}   (a push to the whitelisted org prints nothing = allowed)
printf '{"tool_name":"Write","tool_input":{"file_path":"%s/.claude/settings.json"}}' "$HOME" | /usr/local/lib/cwk/file-guard.sh
# → …"permissionDecision":"deny"…
⛔ What the guard cannot do — verbatim from SECURITY.md
Treat it as best-effort defence in depth, not a security boundary. What it cannot do, stated plainly: it reads the text of one Bash command, so it cannot see inside a script file it is asked to run (bash deploy.sh), a git alias or credential helper defined elsewhere, or a tool other than Bash — and nothing in the hook stops the Edit or Write tool from changing the hook file or settings.json. An organisation that needs the policy enforced installs the hook and its settings.json entries read-only from managed settings, and keeps the whitelist there.

file-guard.sh closes the last clause (the file tools and shell writes to the policy files); the root-owned install closes it again at the OS level. Nothing closes the first: a script file, a git alias, an MCP server or any tool other than Bash remain outside what either hook can read. Branch protection on the team's repositories and the engineer's own credentials scope are the controls that hold when the hook cannot.

A3. Baseline permissions.deny and permission mode per role

The deny list in A2 is the baseline; put it in managed settings, or at least in each engineer's ~/.claude/settings.json. Line by line:

RuleWhy
Read(~/.ssh/**), Read(~/.aws/**)Private keys and cloud credentials never need to be in a model context. (The file-guard blocks writes there; this blocks reads.)
Read(**/.env), Read(**/.env.*)Local secrets. /cwk-scan already skips secret files and records only that one exists; this makes it a rule, not a habit.
Bash(curl *| sh*), Bash(curl *| bash*), Bash(wget *| sh*)Piping a download into a shell is the one-liner every supply-chain incident starts with.
Bash(sudo:*)No privilege escalation from an agent session.
WebFetchNo arbitrary outbound HTTP from the agent. Documentation lookups can go through an approved MCP server instead.
the git … rulesThe same destructive/retargeting commands the hook denies, as a second layer that needs no jq.

A4. GitHub Enterprise Server, proxies, offline use

# 1) gh talks to your GHES host; the kit only ever calls gh read-only unless the hook allows the write
gh auth login --hostname ghe.acme.example --git-protocol https
gh auth status

# 2) the git-guard must know the host, or every push there is "not whitelisted" (see A2 step 2)
ALLOW_HOSTS='ghe\.acme\.example'          # in the root-owned git-guard.sh; add github\.com only if you use both

# 3) proxies — git, gh, npm and Node all honour these; set them in the shell profile or managed env
export HTTPS_PROXY=http://proxy.acme.example:3128
export NO_PROXY=localhost,127.0.0.1,.acme.example

# 4) offline / CDN-blocked networks: keep vendor/ so generated HTML never touches cdnjs
scripts/fetch-vendor.sh --check          # verifies vendor/*.min.js against vendor/SHA256SUMS
scripts/fetch-vendor.sh                  # if missing: pulls through npm (your .npmrc registry / Artifactory) or cdnjs, then verifies

A vendored bundle whose hash does not match the pinned value is never inlined; the generators say so and fall back to the CDN link. On an air-gapped machine, copy a verified vendor/ from a connected one. provenlens (optional call graph) is fully offline as well.

A5. Windows

Both hooks are bash scripts and need jq. They run under Git Bash or WSL only. A Windows install of Claude Code that does not route hooks through one of those has no guard at all — the permissions.deny list from A2 still applies (it is enforced by Claude Code itself), the hooks do not. Treat such a machine as "deny list only" in your risk register, or standardise on WSL, where the Linux path (/etc/claude-code/managed-settings.json) applies inside the distribution.

A6. Data classification — where KB content can end up

A Knowledge Base records permission matrices, unpatched defects, integration auth and env var names, endpoints and business rules. It is derived from the code and easier to read than the code. Every KB now carries a classification in its knowledge-base/_meta.yml: public | internal | confidential | restricted, default internal — a scan asks for a different level only when it can (an interactive session) and never invents public. The export copies it into the hub's _meta.yml and README table, and the hub page shows it as a badge on every project card and a banner above every document (“Internal — contains security findings and configuration for <project>; do not forward outside <org>”; confidential/restricted in red).

Where KB content can goControl
The repo checkout itselfknowledge-base/, cwk-sessions/, .provenlens/ are gitignored (A7). They live only on the machine that ran the scan.
A hub (scripts/kb-export.sh) and its index.htmlThe export refuses a hub repo it can see is public, refuses to overwrite a snapshot from a different repo, runs a secret scan over every page (AWS keys, GitHub/Slack/OpenAI tokens, private keys, user:password@ URLs — a hit skips the project and fails the run; --allow-secrets is the explicit override), strips credentials from remote URLs, and strips the source text from the code graph unless --with-source is passed (which prints a warning). It never commits or pushes.
E-mail, chat, an artifact linkThe hub page is one self-contained HTML file built to be emailed. That is exactly why it carries the classification banner. A confidential/restricted page goes only to people who already have access to the repository it describes.
A pushed hub repoPrivate, same-access-as-the-source only. Never publish a hub of a company repo — not to a public GitHub repo, not to a public Pages site, not to a shared drive with open links.
The model contextInherent (A1). Reading a KB is reading a file.

A7. Repository hygiene

The engineer's global gitignore (Part B, step 3A) protects one machine. A colleague without it, or a CI checkout, will happily commit a knowledge-base/. Put the rule in the team repository itself, or in a pre-commit check, or both:

# .gitignore of every team repo (scripts/onboard-project.sh adds exactly these three lines, idempotently)
knowledge-base/
cwk-sessions/
.provenlens/

# pre-commit / CI check: fail if any of them is staged anyway (git add -f, a rename, a nested copy)
if git diff --cached --name-only | grep -qE '(^|/)(knowledge-base|cwk-sessions|\.provenlens)/'; then
  echo "refusing to commit generated Workflow Kit artifacts (knowledge-base/, cwk-sessions/, .provenlens/)" >&2
  exit 1
fi

Also gitignore CLAUDE.local.md if engineers keep personal notes there. A branch-protection rule with a required status check that runs the snippet above makes it hold for everyone, including bots.

A8. Audit trail

Every notable kit action appends one JSON line to ~/.claude/cwk-audit.jsonl (mode 0600; override the path with CWK_AUDIT_LOG=/var/log/cwk/audit.jsonl, disable with CWK_AUDIT_LOG=off). It never contains command text, file contents or secrets; a value that looks like a URL with credentials is redacted before it is written, and a missing jq or an unwritable path never fails the caller.

FieldMeaning
ts, user, host, cwdISO-8601 UTC time, $USER, hostname -s, working directory.
actionkb.scan, kb.rescan, kb.export, kb.import, kb.pipeline, review, pr.review, pr.prepare, runbook, project.onboard, schedule.install, schedule.remove.
per actionrepo (origin, credentials stripped), commit, depth, classification, hub, code_graph, pr, verdict, preset, cron, …
hook linesThe two guards write to the same file with guard: "git-guard" | "file-guard", tool, decision: deny | allow, and for the git-guard the action (git push, gh pr merge …) and its redacted target. Every deny is logged, and every allowed outward action (a push, a gh write) — so the trail shows what left the machine, not only what was refused.
 
# example lines
{"ts":"2026-09-20T08:14:03Z","user":"nam","host":"mbp-nam","action":"kb.export","cwd":"/srv/work","repo":"https://ghe.acme.example/acme/billing.git","commit":"9f2c1ab","project":"billing","hub":"/srv/kb-hub","classification":"confidential","code_graph":"stripped"}
{"ts":"2026-09-20T08:20:41Z","user":"nam","host":"mbp-nam","guard":"git-guard","tool":"Bash","decision":"deny","action":"","target":"push to a non-whitelisted remote: https://github.com/other-org/x","cwd":"/srv/work/billing"}

# ship it to a SIEM — pick one
tail -F ~/.claude/cwk-audit.jsonl | logger -t cwk-audit               # → syslog → your collector (rsyslog/fluent-bit/Splunk UF)
*/5 * * * * cat ~/.claude/cwk-audit.jsonl >> /srv/siem-drop/cwk-$(hostname -s).jsonl   # cron copy, or point CWK_AUDIT_LOG at the drop folder

The scripts (kb-export.sh, kb-import.sh, kb-pipeline.sh, onboard-project.sh, schedule.sh) log unconditionally; the skills (/cwk-scan, /cwk-rescan, /cwk-review, /cwk-pr, /cwk-runbook) are prompts that are told to call scripts/audit-log.sh when they finish — a prompt can be ignored by a model, so treat skill lines as best-effort and hook/script lines as reliable.

A9. Freshness and depth

A KB is a snapshot. _meta.yml names the commit and the generated date it describes; the hub page shows an amber badge after 30 days and a banner naming the commit, and kb-import.sh warns when that commit is not in the target checkout. /cwk-rescan refreshes only what a git diff touched and rewrites the stamp; scripts/schedule.sh add rescan "0 7 * * 1" <repo> puts it on a weekly cron (read-only skills only — code-editing skills are refused by design).

Depth is the honesty dial. quick and standard sample: on a repository over roughly 40 files, standard reads representative files per layer and says so in _coverage-report.md; a business rule in a file that was not sampled is not in the KB. deep reads every file, gives every module its own document, and records for each rule where it is enforced and whether a test covers it. For a system whose KB will be used to approve changes — or read by security — run deep, and check provenlens in _meta.yml: a KB built on a resolved call graph and one built on grep are not the same claim, and each says which it is.

A10. Approval checklist

  • Company Claude plan is Team/Enterprise; personal Pro/Max accounts are not used for company code.
  • The kit is pinned to a reviewed tag/commit; bash tests/run.sh passes on that revision; updates go through the same review.
  • The surface audit in SECURITY.md was reproduced (no eval, no dynamic require, no telemetry, no secrets).
  • hooks/git-guard.sh and hooks/file-guard.sh are installed root/admin-owned and wired from managed settings; jq is present on every machine.
  • ALLOW_OWNERS/ALLOW_HOSTS in the installed guard name only the company org (and GHES host), or __NONE__.
  • The baseline permissions.deny (A3) is in managed settings; bypassPermissions is not used on company machines.
  • Permission mode per role is documented: engineers acceptEdits, readers the panel's readonly / CLI plan.
  • Windows machines run the hooks under Git Bash/WSL, or are recorded as “deny list only”.
  • vendor/ is present and scripts/fetch-vendor.sh --check passes (no CDN egress from generated HTML); proxy variables are set where needed.
  • Every team repo ignores knowledge-base/, cwk-sessions/, .provenlens/, and a pre-commit/CI check refuses them when staged.
  • Hub repos are private and same-access-as-source; no hub of a company repo is published; --with-source is not used for shared hubs.
  • Classification levels are agreed (internal default; which repos are confidential/restricted) and the hub page shows them.
  • ~/.claude/cwk-audit.jsonl (or CWK_AUDIT_LOG) is shipped to the SIEM; someone reviews decision: deny lines and allowed pushes.
  • KBs used for decisions are deep scans, re-scanned on a schedule, and their _meta.yml commit is checked before use.
  • Branch protection is enabled on team repositories — the control that holds where the hook cannot see.
Part B — Engineer install

B0. Prerequisites

  • Claude Code installed & working: open a terminal and run claude --version to see a version number. (If /plugin is unknown → update Claude Code.)

Use this only on an organization plan (Team/Enterprise). Don't use a personal plan (Pro/Max) for company code — the data policy is different.

It prints the number of skills/commands linked + a reminder of the git-guard config snippet (step B3). Because it's symlinked, later a cd ~/claude-code-workflow-kit && git pull updates everything instantly.

B3. Enable the guards — on a machine without managed settings

If your company deployed A2, both hooks are already active and you can skip to B4 (you will see /hooks list them). Otherwise, arm them yourself:

A

Global gitignore — keep artifacts out of commits

Every knowledge-base/, cwk-sessions/ and .provenlens/ is ignored by git machine-wide (no repo is modified):

touch ~/.gitignore_global
printf '%s\n' 'cwk-sessions/' 'spec-kit-sessions/' 'knowledge-base/' '.provenlens/' 'CLAUDE.local.md' >> ~/.gitignore_global
git config --global core.excludesfile ~/.gitignore_global
B

git guard + file guard — read/sync only, no pushing to team repos, no rewriting the policy files

personal-install.sh has already placed the git guard at ~/.claude/hooks/cwk-git-guard.sh. Now “wire” it into Claude Code: open ~/.claude/settings.json and add the block below (merge it in, don't delete what's there). The file guard is referenced from the kit checkout so a git pull updates it:

{
  "permissions": {
    "deny": [
      "Bash(git remote add:*)", "Bash(git remote set-url:*)", "Bash(git remote remove:*)",
      "Bash(git reset --hard:*)", "Bash(git clean -f:*)", "Bash(git rebase:*)",
      "Bash(git commit --amend:*)", "Bash(git restore:*)", "Bash(git branch -D:*)",
      "Bash(git send-email:*)",
      "Read(~/.ssh/**)", "Read(~/.aws/**)", "Read(**/.env)", "Read(**/.env.*)",
      "Bash(curl *| sh*)", "Bash(curl *| bash*)", "Bash(wget *| sh*)", "Bash(sudo:*)", "WebFetch"
    ]
  },
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash", "hooks": [
        { "type": "command", "command": "~/.claude/hooks/cwk-git-guard.sh", "timeout": 10 },
        { "type": "command", "command": "~/claude-code-workflow-kit/hooks/file-guard.sh", "timeout": 10 } ] },
      { "matcher": "Edit|Write|MultiEdit|NotebookEdit", "hooks": [
        { "type": "command", "command": "~/claude-code-workflow-kit/hooks/file-guard.sh", "timeout": 10 } ] }
    ]
  }
}

Result: allows fetch · pull · status · log · diff · add · commit; hard-blocks pushing to team repos + destructive commands (reset --hard, rebase…); blocks the agent from editing settings.json, the hooks, ~/.gitconfig, .git/config, ~/.ssh, ~/.aws.

🎯 Tune the push whitelist for a company machine
Open ~/claude-code-workflow-kit/hooks/git-guard.sh, the ALLOW_OWNERS / ALLOW_HOSTS lines:
  • To let the AI push to your personal repos: change NamHT4Devlop to your personal GitHub username.
  • Safest (recommended at a company): block the AI from pushing anywhere — set ALLOW_OWNERS='__NONE__'. When you need to push, run it yourself in a terminal.
  • GitHub Enterprise: add your host to ALLOW_HOSTS (A4).
A self-installed guard is a habit, not a policy: you (or the agent, before the file guard is armed) can edit it. Ask your security team for the managed-settings deployment in A2.
🔁 Reload
After editing settings.json, open /hooks once or restart Claude Code so the guards take effect.

🔗 B4b. Optional: provenlens — the call graph

Nothing here needs it. But 27 of the 30 skills use it when a repository has a .provenlens/ index, and grep when it does not — and when they fall back they say so, marking the output ⚠️ grep-depth only (no provenlens index). That sentence is the point: a caller list from grep and one from a resolved call graph are not the same claim, and an impact analysis that hides which one it used is the kind that gets trusted wrongly.

What changes with an index: /cwk-build's >3 callers approval gate is counted from the graph instead of from grep hits; /cwk-review and /cwk-pr list the consumers a diff really reaches together with the tests that already cover them; /cwk-simplify's delete list excludes anything a template names; /cwk-system-map joins a producer in one repo to a consumer in another on a real queue name, across languages.

Covers Java, Ruby, TypeScript and JavaScript only. For Python, Go, C#, PHP, Rust or Kotlin the fallback is the only path, and the skills say so rather than implying coverage they do not have.

git clone git@github.com:NamHT4Devlop/provenlens.git ~/AI-TOOL/provenlens
cd ~/AI-TOOL/provenlens && yarn install
ln -sf ~/AI-TOOL/provenlens/bin/provenlens.js ~/.local/bin/provenlens

B8. Common issues

SymptomFix
Don't see the /cwk-* commandsReload/restart Claude Code; check ls ~/.claude/skills | grep cwk-.
/plugin or /hooks is unknownUpdate Claude Code to a newer build.
A command says “no knowledge-base”Run /cwk-scan once in that repo.
The git guard isn't blockingOpen /hooks or restart to load settings.json. On Windows: are you in Git Bash/WSL? (A5)
Every command is denied with “jq is not installed”Both guards fail closed without jq. Install it (brew install jq / apt install jq).
Push to the company org is deniedThe org/host is not in ALLOW_OWNERS/ALLOW_HOSTS of the installed guard (A2 step 2, A4) — or that is the policy: push from your own terminal.
git clone asks for a passwordPublic repo — clone the HTTPS URL (no auth), or set up an SSH key for the git@ URL.
Map/HTML doesn't render diagramsNeeds Node; with vendor/ present the page is offline. Run scripts/fetch-vendor.sh --check.
kb-export.sh refuses a project: “secret-looking strings”A KB page quoted a token. Remove it at the source (and rotate the token); --allow-secrets only for a confirmed false positive.
